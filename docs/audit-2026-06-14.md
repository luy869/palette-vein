# セキュリティ・コード監査レポート — 2026-06-14

専門レビュアー6体（Go-API / Go-コア / フロント / CLIP / セキュリティ / DB）+ 依存脆弱性監査を**並列実行**した結果を、
重複排除し、**本プロジェクトの実コンテキスト（自宅サーバー・Cloudflare Access 限定公開）で深刻度を再校正**したもの。

> 注: レビュアーは「Critical」を盛り気味（ミドルウェアで防御済みのpanic等を含む）。本レポートの深刻度は
> 「Cloudflare Access で外部未認証アクセスは遮断される」前提で実リスクに引き下げている。
> 残る攻撃面は (a) 招待済みの悪意ユーザー、(b) 自宅LAN内、(c) データ正当性バグ、(d) 依存CVE。

---

## 最優先（高価値 × 低リスク＝すぐ効く）

1. **依存CVE更新**（pillow 6件・requests 2件・react-router・Go stdlib）← 後述§1
2. **DB索引4本追加 + `NOT IN`→`NOT EXISTS`** ← 後述§4。低リスクで検索/推薦が速くなる
3. **画像アップロードのMIME検証**（pillow CVEと連動。招待ユーザーが悪意画像でCLIPを攻撃可能）← §2
4. **CLIPを127.0.0.1バインド + URL allowlist**（SSRF・無認証gRPCをLANから封じる）← §2/§6
5. **HTTPサーバのタイムアウト + JSON body上限**（DoS耐性。CF Access前提で優先度中）← §2

## 対応状況（2026-06-14 実施）

修正・コミット済み（dev機のCLIP gRPCで実測検証）:
- ✅ 画像アップロードのMIME検証（`http.DetectContentType` で image/* のみ許可）
- ✅ HTTPサーバのタイムアウト（ReadHeader/Read/Write/Idle）
- ✅ bcryptパスワード上限（8〜72バイト）
- ✅ CLIPのSSRF対策 = **URL allowlist**（th./w.wallhaven.cc のみ。メタデータ/file:///内部API のブロックを実測確認）
- ✅ **pillow 10.3.0→12.2.0**（6 CVE）・**requests 2.32.3→2.33.0**（2 CVE）。pillow12でEVA02の埋め込み動作確認

**⚠️ 監査の訂正**: レビュアー推奨の「CLIPを127.0.0.1にバインド」は本構成では**不可**
（本番は CLIP=ホスト / backend=Docker で `host.docker.internal` 経由のため、127.0.0.1 だとコンテナから到達不可）。
代わりに **コード = URL allowlist（実施済）＋ 運用 = ホストFW(ufw)で50051を外部遮断** とする。`[::]` バインドは維持。

**実測で却下（重要）**:
- **DB追加索引4本 + `NOT IN`→`NOT EXISTS` は見送り**。dev機(5679行)でEXPLAIN検証した結果:
  - 除外サブクエリ `(user_id,image_id)` は**既存 UNIQUE(user_id,image_id,kind) の prefix で Index Only Scan**
    → 推奨 #1 `feedback_events(user_id,image_id)` は**冗長**（DBエージェントの「索引が無い」は誤り）
  - explore人気順 / getLikes(id降順) / `MAX(fetched_at)` は**いずれも Seq Scan+Sort の方が安い**とプランナが判断（4索引とも未使用）
  - → 現規模では書き込みコストだけ増える。`NOT EXISTS` 書き換えも除外が既存索引で効くため不要。**規模拡大時にEXPLAINで再評価**

**未対応（次回・要判断）**:
- react-router（`npm audit fix`）・Goツールチェーン更新（Dockerベースイメージ更新）
- Go側3修正のHTTPレベル検証（Docker停止中のためビルド/vet検証のみ。復帰後に400応答等を確認）
- JSON body上限・nginxセキュリティヘッダ・キャッシュsingleflight・graceful shutdown 等（フェーズ2）

## 4. DB パフォーマンス（索引・クエリ）

| 深刻度 | 場所 | 内容 |
|--------|------|------|
| **High** | 検索/推薦/発見 計6箇所 | `id NOT IN (SELECT image_id FROM feedback_events WHERE user_id=$1)` → `NOT EXISTS` アンチジョインに。かつ `feedback_events(user_id,image_id)` 索引が**無い** |
| Med | search.go:156 | 色検索が GIN を使えず全件 `unnest`+`bit(24)::int`+`power()` 計算。5万件で重い（中長期は色を `integer[]`/正規化列で前処理） |
| Med | recommend/search.go / search.go | HNSW + `WHERE`(NOT IN, width>height) の post-filter。`hnsw.ef_search` 未設定。フィードバック増で recall 低下 → `AfterConnect` で `SET hnsw.ef_search=100` |
| Med | handlers.go:100 | discover の `ORDER BY RANDOM()` 全件ソート → `TABLESAMPLE` 等で近似化 |
| Low | recommend/search.go:226 | explore の `ORDER BY (views+favorites*3) DESC, RANDOM()` 全件ソート（部分索引で改善可） |
| Low | crawler.go:54,71 | `MAX(fetched_at)` と prune の `fetched_at ASC` ソートに索引なし（起動時のみ実行＝影響小） |

### 追加すべき索引 → **実測の結果、現規模(5679行)では見送り**
> EXPLAIN検証で下記4索引はいずれもプランナに使われなかった（除外は既存UNIQUE索引のprefix、
> 他はSeq Scan+Sortが安い）。書き込みコストに見合わないため追加しない。規模拡大時に再評価する。
> 参考までに候補SQL:
```sql
-- 1. NOT EXISTS サブクエリ + getLikes JOIN に効く（最重要）
CREATE INDEX IF NOT EXISTS feedback_events_user_image_idx ON feedback_events (user_id, image_id);
-- 2. prune / staleOrEmpty の fetched_at
CREATE INDEX IF NOT EXISTS images_fetched_at_idx ON images (fetched_at);
-- 3. explore の人気順（embedding済み・横長限定の部分索引）
CREATE INDEX IF NOT EXISTS images_popularity_idx ON images ((views + favorites * 3) DESC)
    WHERE embedding IS NOT NULL AND width > height;
-- 4. getLikes カーソルページング（任意）
CREATE INDEX IF NOT EXISTS feedback_events_user_likes_idx ON feedback_events (user_id, id DESC) WHERE kind = 'like';
```

## 7. クリーンだった点（良いニュース）

- SQLは全てパラメータ化（インジェクション無し）。色検索のhex変換もユーザー入力ではない
- XSS: React自動エスケープ・`dangerouslySetInnerHTML` 不使用・画像は `referrerPolicy=no-referrer`
- 認証: bcrypt cost=12、JWT httpOnly + SameSite Lax + Secure、管理者はDB二重確認
- 同一オリジン配信でCORS実質無関係。`go build/vet/test`・`tsc/vite build` 全通過
- CRITICAL級（注入・データ破壊・goroutineリーク・到達可能panic）は**発見されず**
