## 1. admin統計の1クエリ化・認証Cookie生成失敗の伝播・パレット集計の修正

**コミット**: `e937e9f`

### 1-1. handleAdminStats: 9回のDB往復を1クエリに統合

**背景**: AdminDashboard は3秒間隔でポーリングしており、1回の表示更新で9個の
`COUNT(*)` / `pg_*_size()` クエリが直列実行されていた（9往復 × 3秒間隔）。

**変更**: スカラーサブクエリで9つの値を単一 `SELECT` にまとめ、1回の `Scan` で取得。
エラー時は `slog.Error` でログを残す。

**効果**: DB往復が 9 → 1。直列実行による累積レイテンシも解消。

### 1-2. setAuthCookie: トークン生成失敗の黙殺を修正

**背景**: `auth.GenerateToken` が失敗した場合、`setAuthCookie` は何もせず return し、
ハンドラは **Cookieなしで 200/201 を返していた**。ユーザーから見ると
「登録/ログイン成功したのに直後の全APIが401」という意味不明な状態になる。

**変更**: `setAuthCookie` が `error` を返すように変更し、register / login の
両呼び出し側で 500 + `slog.Error` を返す。

### 1-3. handleProfilePalette: バブルソート除去 + scanエラーログ

- O(n²) の手書きバブルソートを `sort.Slice` に置換（色数は最大500程度で実害は
  なかったが、標準的でないコードを排除）
- `rows.Scan` 失敗時に黙って `continue` していた箇所に `slog.Warn` を追加
  （部分データ返却の設計は維持）

## 5. 好みベクトルのオンメモリTTLキャッシュ

**コミット**: `68871a4`
**提案**: proposals-2026-06-13.md 提案2（案B採用）

### 背景

`/api/recommend` のたびに `ComputeUserProfile` が実行され、いいね100件分の512次元ベクトル
ロード + スキップ分ロード + 加重平均計算を毎回やり直していた（DBクエリ2回 + O(n×512) 計算）。

### 実装

新規 `backend/internal/recommend/cache.go`:

```go
type ProfileCache struct {
    mu      sync.Mutex
    ttl     time.Duration              // 5分
    entries map[int64]cacheEntry       // userID → (profile, 格納時刻)
}
```

- `Get(ctx, db, userID)`: キャッシュが新鮮ならそれを返す。なければ `ComputeUserProfile` → 格納
- `Invalidate(userID)`: エントリ削除

### 設計判断

| 判断 | 理由 |
|------|------|
| **nil プロフィール（コールドスタート）もキャッシュする** | いいね0件のユーザーが連打してもDBを叩かない。最初のいいねで Invalidate されるので鮮度の問題なし |
| **フィードバック時に必ず Invalidate**（POST/DELETE 両方） | 「いいねした直後におすすめが変わる」既存のUX を維持。TTLは時間減衰の更新が止まらないための保険にすぎない |
| **sync.Mutex の単純な実装**（singleflight なし） | 同時リクエストで二重計算が起きても結果は同じで害がない。個人ユース規模で複雑さに見合わない |
| **Redis ではなくオンメモリ** | 単一プロセス前提（CLAUDE.md の設計方針）。マルチプロセス化したら提案2の案Cに移行 |

### 接続箇所

- `Server` struct に `profileCache` フィールド追加、`NewServer` で `recommend.NewProfileCache(5 * time.Minute)` を生成
- `handleGetRecommend`: `recommend.ComputeUserProfile(...)` → `s.profileCache.Get(...)`
- `handlePostFeedback` / `handleDeleteFeedback`: 成功時に `s.profileCache.Invalidate(userID)`

### k-means との相乗効果

後述の k-means クラスタリングは `ComputeUserProfile` 内で実行されるため、
このキャッシュにより**クラスタリング計算もキャッシュされる**。
キャッシュなしだと毎リクエスト k-means が走るところだった（実装順が重要だった）。

## 6. k-means による好みの複峰性対応【今回の中核変更】

**コミット**: `dc00ee8`
**提案**: proposals-2026-06-13.md 提案7
**変更規模**: 4ファイル、+555行（うちテスト 約230行）

### 背景・動機

好みベクトルは全いいねの加重平均**1本**だった。「サイバーパンク」と「自然風景」の
両方をいいねしているユーザーの場合、平均ベクトルは両者の中間（どちらでもない領域）を
指し、**どちらの系統でもない画像**が推薦されてしまう。

これは設計フェーズ（DEVLOG 2026-05-15）から認識されていた課題で、
「反応が増えたらk-means 2〜3クラスタに分割」という方針が書かれたまま未実装だった。

### アルゴリズム設計

**新規 `backend/internal/recommend/kmeans.go`（全て純粋関数・DBアクセスなし）**

#### スフェリカルk-means

通常のk-means（ユークリッド距離）ではなく、コサイン類似度で割り当てる
スフェリカルk-meansを採用。理由: CLIP埋め込みはL2正規化済みで、
類似検索もコサイン距離（pgvector `<=>`）なので、クラスタリングも同じ距離空間で行うべき。

- **割り当て**: 各点を最もコサイン類似度の高いセントロイドに割り当て
- **更新**: セントロイド = クラスタ内の時間減衰重み付き平均 → L2正規化
- **反復**: 最大20回、割り当てが変化しなくなったら早期終了

#### 初期化: maximin法（k-means++の決定的変種）

1. 最初のセントロイド = 最大重みのいいね（=最も新しいいいね）
2. 2個目以降 = 既存セントロイドとの最大類似度が**最小**の点（最も遠い点）

ランダム初期化を避けた理由: **同じ入力なら同じクラスタ結果になる**（決定的）。
テストが安定し、ユーザーから見ても「リロードするたびに推薦の系統バランスが変わる」
不可解な挙動がない。

#### k の自動選択: エルボー法

```
k=1 の品質を基準に、k=2, 3 と増やして
品質改善が +0.03 未満になったら手前の k を採用
```

- **品質指標**: 各点と所属クラスタセントロイドの平均コサイン類似度
- **ガード条件**: 全クラスタが5メンバー以上ないとその k は不採用
  （外れ値1枚が独立クラスタになるのを防ぐ）

#### 閾値定数（チューニングポイント）

```go
clusterMinLikes  = 30   // クラスタリング開始のいいね数（それ未満は1クラスタ）
maxClusters      = 3    // 最大系統数
minClusterSize   = 5    // クラスタとして認める最小いいね数
clusterMinGain   = 0.03 // kを増やすのに必要な品質改善
kmeansIterations = 20
```

`clusterMinLikes=30` は設計書の「反応30件」に合わせた。
`clusterMinGain=0.03` は合成データでの動作確認値であり、実データでの調整余地がある
（小さくするほど分割されやすい）。

### データフローの変更

```
ComputeUserProfile（profile.go）
  ├─ いいね/スキップのベクトルロード（従来どおり）
  ├─ Vector: 全いいねの加重平均（従来どおり維持 — コールドスタート判定・後方互換）
  └─ Clusters: buildClusters()                       ← 新規
        ├─ clusterLikes() で系統分割（30件未満なら1クラスタ）
        └─ 系統ごとに computeProfileVector()
            ・Rocchio負例（スキップ）は全系統に共通で適用
            ・Share = 系統の重み合計 / 全体の重み合計

Search（search.go）
  ├─ クラスタごとに querySimilar()（HNSW検索 × クラスタ数）
  ├─ allocateCounts(): 推薦枠19件をShareに比例配分（最大剰余法・各系統最低1件）
  ├─ mergeClusterCandidates(): 配分数ずつ取得、画像ID重複は除外、
  │                            不足分は他系統の余りからスコア順に補填
  └─ 探索枠5件・シャッフル・推薦理由計算（従来どおり）
```

### 設計判断の詳細

| 判断 | 内容と理由 |
|------|-----------|
| **UserProfile.Vector を残す** | コールドスタート判定（nil チェック）と将来の後方互換のため。クラスタが空の場合のフォールバックも Vector で行う |
| **Rocchio（スキップ減算）は系統別にしない** | スキップがどの系統への否定かは判別できない（中間の画像かもしれない）。全系統に一律適用が安全 |
| **推薦理由は従来どおりグローバル計算** | 系統Aの推薦画像に最も近いいいね画像は自然に系統Aのものになる。系統別に理由を制限するコードは不要だった |
| **配分は最大剰余法 + 各系統最低1件** | 少数派の系統（Share 5%等）も必ず1件は推薦に出る。「あの系統が完全に消えた」を防ぐ |
| **API レスポンス形式は不変** | mode/items/reason_images_lookup の構造は変更なし。フロントエンドの変更不要。クラスタ情報の可視化は次回候補 |
| **HNSW検索がクラスタ数分（最大3回）走る** | 1回あたり数ms（HNSW）なので許容。プロフィールキャッシュにより k-means 自体は5分に1回しか走らない |

### テスト（kmeans_test.go、13ケース追加）

| テスト | 検証内容 |
|--------|---------|
| `TestClusterLikesBelowThreshold` | 30件未満は分割されない |
| `TestClusterLikesSingleTightCluster` | 同一方向40件は k=1 のまま（過剰分割しない） |
| `TestClusterLikesTwoSeparatedGroups` | 直交2系統（20+20件）が正しく2分割され、混在しない |
| `TestClusterLikesDeterministic` | 同入力→同出力（決定性） |
| `TestBuildClustersShares` | 30:10 の系統で Share 合計が1.0 |
| `TestAllocateCounts`（5ケース） | 比例配分・最低1件保証・合計の正確性 |
| `TestMergeClusterCandidates`（3ケース） | 系統間の重複除去・不足時の補填・低スコア系統の枠保証 |
| `TestLeftoverCandidates` | 未使用候補のスコア順抽出 |

既存テスト13件も全て通過（`computeProfileVector` 等のシグネチャは不変）。

### 既知の制約・次回への引き継ぎ

1. **実データでの `clusterMinGain` 調整が未実施**。実際のいいねデータで k=2 になる頻度を
   観察し、分割されすぎ/されなさすぎがあれば 0.02〜0.05 の範囲で調整する
2. **クラスタ情報のUI可視化は未実装**。「あなたの好みは2系統あります」のような表示や、
   推薦カードへの系統バッジ追加は効果的だが、APIレスポンス拡張が必要（次回候補）
3. **k-meansの計算量**: O(iterations × k × n × 512)。いいね90日分（最大数百件）なら
   1ms未満だが、feedbackWindowDays を伸ばす場合は注意

## 7. タブ切替でデータ・スクロール位置を保持（KeepAlive方式）

**コミット**: `8cdf833`
**Explore指摘**: フロント調査 #1（効果:高）。前回も「次回候補の筆頭」とされていた項目。

### 背景

各グリッドは `<Routes>` 配下にあり、タブを切り替えると**アンマウントされて
state が破棄**されていた。「発見タブで20件スクロールして気になる画像を見つけ、
おすすめタブを覗いて戻ると、最初からやり直し」という探索の流れを断つ問題。
無限スクロールで積み上げた `displayedIds` / `nextCursor` も毎回リセットされていた。

### 実装

`App.tsx` のルーティングを `<Routes>/<Route>` から自前の表示制御に変更。

**KeepAlive コンポーネント**:
```tsx
function KeepAlive({ active, children }) {
  const [mounted, setMounted] = useState(active)
  useEffect(() => { if (active) setMounted(true) }, [active])
  if (!mounted) return null
  return <div style={active ? undefined : { display: 'none' }}>{children}</div>
}
```
- 初回アクティブ時にマウントし、以降は `display:none` で**DOMごと保持**する
  （アンマウントしないので state も DOM スクロール位置も残る）

**保持対象の選定**:
```tsx
const KEEP_ALIVE_TABS = ['discover', 'recommend', 'search', 'likes']
```
| タブ | 扱い | 理由 |
|------|------|------|
| 発見/おすすめ/検索/いいね | 保持 | 無限スクロールの蓄積を維持したい |
| パレット | 毎回再マウント | いいね後に古い集計を見せないよう鮮度優先 |
| 管理 | 毎回再マウント | 3秒ポーリングがバックグラウンドで走り続けるのを防ぐ |

**スクロール位置の記録と復元**:
```tsx
const scrollPos = useRef<Record<string, number>>({})
// scroll イベントで scrollPos[currentTab] = window.scrollY を記録
// useLayoutEffect で currentTab 変化時に window.scrollTo(0, scrollPos[currentTab] ?? 0)
```
`useLayoutEffect` を使うのは、`display` 切替が DOM に適用された直後・描画前に
スクロールを復元してちらつきを防ぐため（子の layout effect → 親の順で走るので
復元時には既に表示が確定している）。

### 各タブを個別 ErrorBoundary で包む副次効果

旧構造は `<Routes>` 全体を1つの ErrorBoundary で包んでいた。KeepAlive 化で
**各タブを個別の ErrorBoundary で包む**ようにしたため、1タブの描画クラッシュが
他タブに波及しなくなった。

### 付随修正: SearchGrid の hex ディープリンク

色パレット → 色検索の連携（`navigate('/search?hex=...')`）は、SearchGrid の
`useEffect([], ...)` で初回マウント時のみ hex を読んでいた。KeepAlive で
**常駐するようになると2回目以降のクリックで再実行されない**ため、
`useEffect([hexParam], ...)` に変更して hex 変化のたびに発火するようにした。
これは KeepAlive 対応であると同時に「パレットの色を連続クリックしても毎回反映」
という単体の改善でもある。

## 8. 画像モーダルに前後ナビゲーション（矢印キー対応）と位置表示【中核変更】

**コミット**: `93742dc`
**Explore指摘**: フロント調査 #2（効果:高）。前回「次回候補」とされた項目。
**変更規模**: 8ファイル、+172/-31行

### 背景

拡大モーダルは1枚を表示するだけで、見比べるには一度閉じて別のサムネを
クリックし直す必要があった。「この系統の画像を続けて見たい」という
ギャラリーサービスの基本的な探索欲求に応えられていなかった。

### アーキテクチャ上の課題と判断

**問題**: `ImageCard` と `RecommendCard` は**各カードが自前の `showModal` state を持ち**、
自分1枚の画像しか知らなかった（兄弟カードの文脈がない）。前後ナビゲーションには
「一覧の中での現在位置」が必要なので、この構造では不可能。

**判断**: モーダルの状態管理を**カードからグリッドへリフトアップ**する。
グリッドは一覧（`images`）を持っているので、index と前後移動を管理できる。

### 共通フック `useImageModal`

`src/lib/useImageModal.ts`（新規）:
```ts
export function useImageModal(images: Image[]) {
  const [index, setIndex] = useState<number | null>(null)
  const open = useCallback((id) => { /* findIndex で開く */ }, [images])
  const close = ...
  const prev = ...  // index を1減らす（下限ガード）
  const next = ...  // index を1増やす（上限ガード）
  return { image, index, total, open, close, prev, next, hasPrev, hasNext }
}
```

**設計判断**:
| 判断 | 理由 |
|------|------|
| **open は id 起点、保持は index** | 無限スクロールで一覧末尾が伸びても、開いている位置がずれない（末尾追加は既存indexに影響しない） |
| **モーダルをグリッドに1つだけ描画** | カードごとにモーダルを持つ旧構造を廃し、グリッド単位で1インスタンス |
| **全4グリッドで同一フックを共有** | ImageGrid/SearchGrid/LikesGrid は `images`、RecommendGrid は `items.map(i => i.image)` を `useMemo` で渡す |

### ImageModal の拡張

## 10. 拡大画像が頻繁に403で表示されないバグの修正【調査記録】

**コミット**: `59b8e88`
**報告**: 「拡大表示すると結構な頻度でエラーが起こって表示されない」

### 切り分けプロセス（誤診を避けるための段階的検証）

| ステップ | 検証 | 結果 |
|---------|------|------|
| 1 | `images.url` の構築箇所を確認 | `res.Path`（API提供の正しい元画像URL）。構築ミスではない |
| 2 | DBから実URLをサンプル | `https://w.wallhaven.cc/full/XX/wallhaven-ID.ext`、拡張子も正しい |
| 3 | 5件を curl（Refererなし/localhost Referer） | 全て200。最初は再現せず |
| 4 | **25件に増やして実測**（GET・ステータス/サイズ/時間） | **9/25 = 36%が403**。「結構な頻度」を再現 |
| 5 | 403応答のヘッダ確認 | Cloudflare が `text/html` の403ページを返却（画像本体でない） |
| 6 | 拡張子を入れ替えて再試行 | 同じく403。拡張子ミスではない（404でもない） |
| 7 | **ブラウザUA + Referer:wallhaven.cc で再試行** | 全て200。UAかRefererが原因と判明 |
| 8 | **Refererヘッダなしで再試行** | 全て200。**Referer が原因と確定** |

### 根本原因

**Wallhaven（Cloudflare）の Referer ベースのホットリンク保護**。

- サムネは `th.wallhaven.cc` 配信で保護対象外 → グリッドは常に正常
- 元画像は `w.wallhaven.cc/full/...` で、**約36%の画像が外部オリジンの Referer を拒否**
- ブラウザはモーダルから画像を読むとき `Referer: http://localhost:5173/` を送る
  → 保護対象の画像が **403 Forbidden** → モーダルが空表示

| リクエスト条件 | HTTPステータス |
|---------------|---------------|
| `Referer: http://localhost:5173`（修正前のブラウザ動作） | **403** |
| `Referer: https://wallhaven.cc/` | 200 |
| Referer ヘッダなし | 200 |

### 修正

全ての Wallhaven 画像 `<img>` に `referrerPolicy="no-referrer"` を付与し、
ブラウザが Referer を送らないようにした（403回避）。
加えてモーダルには `onError` で `thumb_url` へのフォールバックを追加し、
削除済み画像など他要因で失敗しても空表示にならないようにした。

- `ImageModal.tsx`: フル画像に `referrerPolicy` + `onError` フォールバック
- `ImageCard.tsx` / `RecommendCard.tsx`（サムネ+推薦理由）/ `LikesGrid.tsx`: サムネに `referrerPolicy`
  （現状は動作しているが、Wallhaven が将来サムネにも保護を広げた場合に備えた正しいポリシー）

### なぜプロキシ/APIキーにしなかったか

| 案 | 不採用理由 |
|----|-----------|
| バックエンドで画像プロキシ | サーバー側 curl も403になる（Refererなしで投げれば200だが、最大11MB級の画像を全件中継するのは帯域・レイテンシの無駄）。referrerPolicy で解決するなら中継は過剰 |
| Wallhaven APIキー | APIキーは api/v1 用で、画像CDN（Cloudflare）の403には効かない。`<img src>` にキーを載せるとクライアントに漏れる |
| referrerPolicy=no-referrer | **1属性で解決・追加コストゼロ・秘密情報なし**。採用 |

### 教訓（面接で語れる切り分けの勘所）

- 最初の5件が偶然すべて200で「再現しない」状態だった。**サンプルを増やして実測**したことで
  36%という再現率が見え、初めて問題が掴めた（小サンプルでの「直った」は危険）
- 403 を見て即「ホットリンク」と決めず、**UA/Referer を1つずつ変えて二分探索**し、
  curl の UA が原因という誤診を回避してから Referer に確定させた
