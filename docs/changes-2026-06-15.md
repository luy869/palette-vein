## B. 埋め込みモデル EVA02-B/16 → **EVA02-L/14（512→768次元）**

### 動機
1660 Ti(6GB)に対しB/16はVRAM約700MBと余裕。デプロイ直後でDBがほぼ空＝再埋め込みが安価な好機。
Base→Largeで画像エンコーダが明確に強化（レコメンド核＝画像→画像に直結）。同系統なのでコード変更は最小。
※ いいねが溜まるまでは推薦品質はデータ量律速。劇的改善ではなく「安いうちの土台底上げ」という位置づけ。

### 変更点
- `clip_service/server.py`: `MODEL_NAME="EVA02-L-14"` / `PRETRAINED="merged2b_s4b_b131k"`（768次元・224px。
  open_clip で実在タグと次元を確認済み）。ウォームアップは前回の汎用化（preprocess 由来）でそのまま動作。
- `backend/migrations/008_change_embedding_dim_768.sql`（新規）: `embedding` を VECTOR(512)→VECTOR(768) に作り直し、
  HNSW/pending 索引を再作成、`embed_errors=0` で全画像を再埋め込みさせる。
  **冪等性が肝**: 本プロジェクトの移行は毎起動で全SQL再実行されるため、素朴な DROP/ADD だと毎回 768 を破棄してしまう。
  `format_type(atttypid,atttypmod) <> 'vector(768)'` を DO ブロックで判定し、**既に768なら何もしない**。
- `backend/internal/recommend/profile.go`: `const embedDim = 512` → `768`（kmeans.go も参照）。
- `backend/internal/recommend/profile_test.go`: 512ハードコードを `embedDim` 基準に修正。

### 検証
- `go build ./... && go vet ./... && go test ./internal/recommend/` 全green。
- 移行008を使い捨て pgvector(pg16)で実地テスト: 512→768変換・embedding NULL化・embed_errors リセットを確認。
  768を入れてから**再実行しても768を保持（破壊しない）**＝冪等を確認。索引も正しく再作成。

### 本番反映手順（順序重要）
1. `git pull`
2. **CLIPを先に L/14 に切替**: run-clip.sh を Ctrl+C → 再実行（初回はL/14重み約1.7GBをHFからDL → `loading CLIP EVA02-L-14` → `model ready`）。
   ※ 先に CLIP を上げないと、embedder が 512 次元を 768 列へ挿入しようとして失敗する。
3. `./start.sh`（backend が embedDim=768 で再ビルド、移行008が走り 512→768＋再埋め込みtrigger）。
4. CLIPログで `dim=768` を確認。管理タブの「埋め込み済み%」が再び 0 から増えていく。
