## 0. 現状の強み（まず土台の確認）

- 推薦の中核が実装済み: 時間減衰 + Rocchio + **k-means複峰性対応** + ε-greedy探索 + 推薦理由可視化
- 埋め込みは **EVA02-B/16**（512次元・高品質）。テキスト/画像/色の3検索 + pgvector HNSW
- 信頼性: タイムアウト・slog構造化ログ・Error Boundary・楽観的UI + undo・レート制限中央管理
- デプロイ一式（prod compose・Cloudflare Tunnel/Access・ランブック）と通しテスト済み
- モデル比較ハーネス・好みベクトルの純粋関数テスト（26ケース）

## 1. 既知の課題・技術的負債

### バックエンド
| 課題 | 内容 | 出典/状態 |
|------|------|-----------|
| API統合テスト不在 | recommend の純粋関数のみテスト。ハンドラ/認証/DBは未テスト | proposals #6（認証のhttptestのみ採用方針） |
| `NOT IN` サブクエリ | 検索/推薦/発見の6箇所。大量フィードバックで遅くなる可能性 | proposals #3（要 EXPLAIN 実測→ NOT EXISTS 化） |
| プロフィールキャッシュ単一プロセス前提 | オンメモリTTL。マルチプロセス化したら Redis が必要 | 設計上の割り切り |
| embedder のドロップ | キュー満杯時に drop（catchup が回収）。優先度なし | proposals #4（見送り・ボトルネックはDL） |
| k-means 閾値 | `clusterMinGain=0.03` は合成データ調整値 | 実データで分割頻度を観察し調整 |
| 色検索の距離 | RGB二乗距離。知覚的には CIELAB(ΔE) の方が自然 | 未着手 |

### フロントエンド
| 課題 | 内容 | 出典 |
|------|------|------|
| エラー表示が不統一 | inline段落 / Toast / グリッド置換が混在。見落としやすい | proposals-frontend #C（AlertBox共通化・採用推奨） |
| サムネがキーボードで開けない | `<div onClick>` でフォーカス不可。a11y欠如 | proposals-frontend #F（採用推奨） |
| ライトモードが中途半端 | トグルはあるが `.card` 等の light スタイル未定義 | proposals-frontend #A（廃止推奨） |
| モバイル未最適化 | ホバー前提UI・タッチターゲット小・レスポンシブ未調整 | proposals-frontend #B |
| 検索状態がURL非同期 | リロード/共有で検索条件が消える（色のhexのみ対応） | proposals-frontend #G（優先度低） |

### AI / 推薦
| 課題 | 内容 |
|------|------|
| 日本語検索が弱い | EVA02は英語中心。日本語クエリは精度が落ちる（SigLIP i18n は今回見送り） |
| 画像→画像の多様性 | DINOv2（視覚的類似）ハイブリッドは見送り。フィルターバブル回避の余地 |
| 推薦の評価指標が**一部実装**（2026-06-14） | いいね率・カバレッジ・アクティブ率は管理画面に追加済み。多様性スコア・発掘率は未着手 |

### インフラ / 運用
| 課題 | 内容 |
|------|------|
| CI/CD 無し | build/test は手動。GitHub Actions等で自動化余地 |
| DBバックアップ戦略無し | feedback_events/users が消えると痛い（images はクロールで再生成可） |
| GPU互換 | 本番1070はcu128非対応 → 1650S固定 or 本番だけcu126（DEPLOY.md参照） |
| 監視・ログ集約無し | slogはあるがダッシュボード/アラート無し |
| 手動起動（systemd無し） | ゲーム併用のため意図的。常時公開には常駐方式の再検討が必要 |

## 3. セキュリティの留意点

| 項目 | 現状 | 改善余地 |
|------|------|----------|
| レート制限 | httprate（IPベース、認証は10/min・全体300/min） | ユーザー単位/エンドポイント別の細分化 |
| CSRF | SameSite=Lax のみ | 状態変更APIにCSRFトークン（同一オリジン配信なら優先度低） |
| 入力バリデーション | 一部のみ（admin pages の負数等） | 検索クエリ長・hex形式などの境界チェック強化 |
| シークレット | JWT_SECRET存在チェックのみ | 長さ強制・ローテーション方針 |

## 4. 将来の機会（差別化・成長）

- **DINOv2ハイブリッド**: CLIP（意味）+ DINOv2（視覚/構造）のスコア融合。多様性/探索枠に効く可能性（比較で「違う画像を返す率が高い」と確認済み）
- **評価指標ダッシュボード**: 推薦品質を数値で可視化 → チューニングの土台＋面接で強い題材
- **クラスタ系統のUI可視化**: 「あなたの好みは2系統」表示・推薦カードへの系統バッジ（k-means結果の露出）
- **モデルアップグレード経路**: 768次元（EVA02-L/14 等）への引き上げはスキーマ変更でOK（次元の真実源は `recommend/profile.go embedDim` + migration）
- **多言語検索**: SigLIP i18n（日本語に強い・客観指標0.829で最高）。テキスト検索を強化するなら有力

## 5. デプロイのリスク・チェックリスト

- **GPU互換**: 1070はcu128不可 → 1650S固定 or 本番だけcu126（要実機確認）
- **Wallhaven**: ホットリンクは referrerPolicy で403回避済みだが、ToSの最終確認。匿名45 req/min
- **既存チャットボットとの共存**: ポート（8090）・GPU住み分け・トンネルingress追記のみ
- **HTTPS必須**: Secure Cookie のため。ローカルテストは `SECURE_COOKIE=false`
- **隔離/撤去**: 別composeプロジェクト・専用ボリューム・即 down -v 可能

---

## 6. 推奨優先度（GPTの「まず動かす」助言も踏まえて）

1. **デプロイして実ユーザー反応を見る**（モデル選定で悩むより、まず公開してデータを集める）
2. **評価指標ダッシュボード**（推薦品質を測れるように。改善のループが回り始める）
3. **フロントの仕上げ**: エラー表示統一(#C)・サムネa11y(#F)（小さく効く）
4. **反応次第で**: DINOv2ハイブリッド（多様性）or 多言語検索（SigLIP）or モデル引き上げ
5. **運用**: CI/CD・DBバックアップ（公開後の安定運用に）

> モデルやアルゴリズムを磨くより、**測る仕組み（評価指標）→ 公開 → データ収集**のループを先に作る方が、
> 結果的に推薦品質の改善が速い。
