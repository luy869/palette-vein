# PaletteVein — 面接用プロジェクトガイド

好みを学習しながら壁紙イラストを発掘するWebサービス。
推薦理由の可視化（なぜこの画像がすすめられているか）が差別化点。

---

## エレベーターピッチ（状況別）

### 30秒版
> 「CLIPという画像認識AIと、ベクトルデータベースを使って『好みを学習する壁紙サービス』を作りました。画像をいいね/スキップするたびにユーザーの好みベクトルが更新されて、次第に自分好みの推薦になっていきます。推薦理由として『この壁紙を気に入ったのはこの画像に似ているから』という根拠画像も表示しています。」

### 2分版（技術面接向け）
上記に加え:
> 「バックエンドはGo、AIはPythonのCLIPをgRPCで連携、DBはPostgreSQL + pgvectorです。技術選定の理由として、GoとPythonの連携にHTTPではなくgRPCを選んだのは、Protobufによる型安全性と、将来的にGPUサーバーを分離する際の拡張性を見越してです。pgvectorはRedisなど専用ベクトルDBを使わずにPostgreSQLだけで完結できるため、運用負荷を下げられます。推薦アルゴリズムはRocchioアルゴリズムにε-greedyを組み合わせて、フィルターバブルを防ぎながら精度を上げる設計にしました。」

---

## 技術スタック（面接での説明ポイント）

| 技術 | 選んだ理由 | 代替と比較した点 |
|------|-----------|----------------|
| **Go（バックエンド）** | 並列処理性能。goroutineで埋め込みキューとクローラーを並行実行 | Python FastAPIも候補だったが、gRPCクライアントとHTTPサーバーの並列性でGoが優位 |
| **Python + CLIP（AI層）** | AIライブラリのエコシステムはPythonが圧倒的。CLIPはタグに依存しない「雰囲気」の類似検索が可能 | PyTorch + open_clip（ViT-B/32）。CPU環境でも動作する |
| **gRPC（Go-Python連携）** | 型安全（Protobuf定義）、将来のGPUサーバー分離への拡張性 | HTTPでサブプロセス呼び出しも候補だったが、型のあいまいさとレイテンシで劣る |
| **PostgreSQL + pgvector** | RDBとベクトルDBを1システムで管理。JOINでフィードバックとベクトルを結合できる | 専用ベクトルDB（Pinecone/Qdrant）は運用コストが高く、RDBとの2重管理になる |
| **React + TypeScript** | コンポーネント化と型安全でUI複雑度を管理しやすい | — |

## 面接で深掘りされやすいトピック

### 1. 推薦アルゴリズム

**どう話すか**:
> 「ユーザーのいいね画像のCLIPベクトルを時間減衰付き重み付き平均で合成して好みベクトルを作ります。スキップはRocchioアルゴリズムで負の方向に軽く引きます（係数0.2）。これで『好きだけど飽きてきた系統』をスキップすることで推薦から遠ざけられます。探索/活用バランスはε-greedy（20%探索）で、人気画像をランダムに混ぜてフィルターバブルを防いでいます。」

**補足（聞かれたら）**:
- 時間減衰: 半減期9.7日。直近のいいねが強く効く
- コールドスタート: いいね10件未満はWallhaven人気順（toplist）にフォールバック
- 推薦理由: いいねした画像群のベクトルをメモリにロードしてcosine類似度top-2を推薦理由として表示（DBアクセスなし）

### 2. HNSWインデックスと近似最近傍探索

**どう話すか**:
> 「pgvectorのHNSWインデックスを使っています。5万件程度のデータなら全件スキャン（IVFFlatより遅くなる境界）でも問題ないですが、HNSWの方がパラメータチューニング（m=16, ef_construction=64）で精度と速度のバランスが取りやすい。実際のクエリは類似度上位40件を取って探索枠と合わせて24件返しています。」

### 3. 並列処理設計

**どう話すか**:
> 「埋め込みキューはバッファ付きチャンネル（256件）で実装して、HTTPリクエストをブロックしないようにしています。クローラーはgoroutineで独立して動き、1.5秒間隔のレート制限を`sync.Mutex`で中央管理しています。管理画面からのアドホッククロールと定期クロールが同時に走ってもWallhavenの45 req/minを超えないように、予約方式（次回呼び出し可能時刻を記録）で制御しています。」

### 4. 色検索のSQL最適化

**どう話すか**:
> 「当初はGoで全件ロードしてRGB距離をソートしていましたが、PostgreSQLにプッシュダウンしました。16進数カラーコードを`('x' || hex)::bit(24)::int`でビット演算で整数変換して、unnestで展開した色配列の最小距離をSQL内でORDER BYしています。1.2万件で32msに改善されました（EXPLAIN ANALYZEで実測）。」

### 5. gRPC + Go-Python設計

**どう話すか**:
> 「`protos/clip.proto`でインターフェースを定義して、GoとPythonそれぞれにコード生成しています。`EmbedText`（テキスト→512次元ベクトル）と`EmbedBytes`（画像バイナリ→ベクトル）の2エンドポイントです。GoからはgRPC遅延接続で接続して、CLIPサービスが起動していなくてもGoサーバーは起動できます。」

### 6. 好みの複峰性とk-meansクラスタリング【一番強い話題】

**問題提起から話すと刺さる**:
> 「好みベクトルを全いいねの加重平均で1本作っていたんですが、これには根本的な欠陥があります。例えば『サイバーパンクな街並み』と『静かな自然風景』の両方が好きなユーザーの場合、平均を取ると両者の中間、つまり**どちらでもない**ベクトルになってしまう。結果、本人が好きな2系統のどちらにも当てはまらない画像が推薦される。」

**解決策**:
> 「いいねが30件を超えたら、いいねベクトル群をスフェリカルk-meansで2〜3系統にクラスタリングします。通常のk-meansじゃなくコサイン類似度版を使うのは、CLIP埋め込みがL2正規化されていて、pgvectorの類似検索もコサイン距離だから、クラスタリングも同じ距離空間で揃えるべきという理由です。系統ごとに類似検索して、推薦枠24件を各系統のいいね数に比例配分する。少数派の系統も最低1枚は必ず出すようにして、好みが埋もれないようにしています。」

**こだわった点（聞かれたら）**:
- **kの自動選択**: エルボー法。k=1から増やして平均類似度の改善が閾値（0.03）を下回ったら手前で止める。外れ値1枚が独立クラスタにならないよう最小5件のガードも
- **決定的にした**: k-means++のランダム初期化ではなく、最も重みの大きいいいねを起点に「最も遠い点」を順に選ぶmaximin法。同じ入力なら同じ結果になり、テストが安定し、ユーザーから見ても推薦の系統バランスがリロードで変わらない
- **純粋関数として実装**: DBアクセスを排してクラスタリングを純粋関数にしたので、合成データでtable-drivenテストが書ける（13ケース追加）
- **キャッシュとの相乗効果**: k-means計算は好みベクトルキャッシュ（5分TTL）に乗るので毎リクエストは走らない

## 苦労した点・解決策

| 問題 | 解決策 |
|------|--------|
| **pgvector型スキャン** | `rows.Scan(&vec)`のターゲットとして`*[]float32`は非対応。`pgvector.Vector`型でスキャン後`.Slice()`で変換する必要があった |
| **open_clipの依存競合** | pip installでバージョンピンを付けると`ResolutionImpossible`。ピンを外すことで解決 |
| **gRPCのモジュールパス** | Python側で`from generated import clip_pb2`にすると`clip_pb2_grpc.py`内部の`import clip_pb2`が絶対インポートで解決できない。`sys.path.insert`で解決 |
| **Wallhaveレート制限超過** | クローラーと管理画面が同時実行すると制限を超える可能性。Clientに予約方式のMutexを追加して中央管理 |
| **楽観的UIでのundo実装** | 削除前のカードインデックスを保持して`splice(Math.min(idx, next.length), 0, removed)`で元の位置に戻す |
| **平均ベクトルの複峰性問題** | 好み2系統の中間を指してしまう問題をk-meansクラスタリングで解決（上記トピック6） |
| **タブ切替でデータが消える** | `<Routes>`はアンマウントする。KeepAlive（display:none）でDOMごと保持し、スクロール位置も復元 |
| **モーダル前後ナビの設計** | カードが自前でモーダルを持つ構造では「一覧内の位置」が分からない。状態をグリッドにリフトし共通フック化して解決 |
| **拡大画像が3割方403で出ない** | サムネは出るのにモーダルの元画像が頻繁に失敗。25件実測で36%が403と判明 → UA/Refererを1つずつ変えて二分探索し、Wallhavenの**Refererベースのホットリンク保護**と特定。`referrerPolicy="no-referrer"`で解決（詳細は下記） |

## 数字・規模感

| 指標 | 値 |
|------|---|
| DBの画像数 | 最大5万件（自動プルーニング） |
| CLIP埋め込み次元数 | 512次元（ViT-B/32） |
| 推薦件数 | 1リクエストで24件（類似19件 + 探索5件） |
| クラスタリング発動 | いいね30件以上で k-means（最大3系統）。好みベクトルは5分TTLキャッシュ |
| 色検索クエリ時間 | 1.2万件で32ms（SQL内ソート） |
| JWT有効期限 | 30日（httpOnly Cookie） |
| Wallhavenレート制限 | 45 req/min（APIキーなし）、リクエスト間隔1.5秒で対応 |
| CLIP推論速度 | 1枚2〜5秒（CPU環境）、バックグラウンドキューで非同期処理 |
| マイグレーション | 起動時に`migrations/*.sql`を順次実行（冪等） |

## 今後やりたいこと（聞かれたとき）

> 注: クラスタリングによる複峰性対応とプロフィールキャッシュは**実装済み**（トピック6参照）。
> 「やりたいこと」として挙げず、「やったこと」として語る。

1. **クラスタ系統のUI可視化**: 現在クラスタリングは内部処理のみ。「あなたの好みは2系統あります」という表示や、推薦カードへの系統バッジを付けると透明性がさらに上がる（APIレスポンス拡張が必要）
2. **評価指標の実装**: いいね率・多様性スコア（平均ペアワイズcosine距離）・発掘率（人気順下位からのいいね割合）を管理画面に追加
3. **GPU分離**: gRPCで既にサービス境界があるので、CLIP推論をGPUインスタンスに切り出すだけで完了
4. **Wallhaven APIキー取得**: 認証なしは45 req/min制限。APIキーで制限が緩和される
5. **クラスタ閾値の実データ調整**: k分割の感度（改善閾値0.03）は合成データでの値。実利用データで分割頻度を観察して調整したい

## アーキテクチャ図（口頭説明用）

```
ブラウザ（React）
    ↕ HTTP / Cookie (JWT)
Goサーバー（:8080）
    ├─ chi ルーター
    ├─ AuthMiddleware (JWT検証)
    ├─ API ハンドラ群
    │   ├─ /api/recommend  → 好みベクトル（5分TTLキャッシュ）→ k-means系統分割 → 系統別pgvector検索
    │   ├─ /api/search     → CLIP埋め込み → pgvector検索
    │   ├─ /api/search/color → SQL内RGB距離ソート
    │   └─ /api/feedback   → 楽観的UI前提、undo対応（成功時プロフィールキャッシュ無効化）
    ├─ クローラー goroutine（24時間周期）
    └─ 埋め込みキュー goroutine（256バッファ）
           ↕ gRPC (:50051)
       CLIPサービス（Python）
           ├─ EmbedText（テキスト → 512次元）
           └─ EmbedBytes（画像バイナリ → 512次元）
    ↕ pgx/v5
PostgreSQL 16 + pgvector
    ├─ images（VECTOR(512) HNSW）
    ├─ feedback_events
    └─ users
```
